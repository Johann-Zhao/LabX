# LabX 智能体交互工作流（对话环节的规范）

> 本文件是智能体对话（`/api/agent/chat` 与前端"智能助手"页）的**交互契约**。
> 修改对话行为先改这里，再改 `backend/orchestrator.py`。
> 制定背景：模糊提问不能硬答（"我的电机不转"没说是什么电机）；本地知识库不可能覆盖所有物料，需要联网兜底。

## 三条原则

1. **先问清楚，再回答。** 回答所需的关键信息（槽位）缺失时，禁止直接给方案——先反问。
2. **本地优先，网络兜底，通用经验最后。** 本地知识库有的不用网络；网络检索不到的才用模型通用知识。
3. **每个回答必须标明出处**（provenance）：`local_kb` 本地知识库 / `web` 网络检索 / `model` 通用经验 / `offline` 离线兜底。

## 主流程（状态机）

```
用户消息
  → 意图识别（troubleshoot / recommend / inventory / chitchat）
  → 分支：
```

### troubleshoot（排障）

槽位：**故障物料**（必答）、**故障现象**（必答，要具体）

1. 从用户当前借用清单 + 消息文本定位物料（名称/型号/特征词匹配，匹配分见 orchestrator）
2. **进入澄清的三种情况**（满足其一就问，一轮问全）：
   - **物料定位不到**（借用清单与目录都无匹配）
   - **物料只是弱匹配**（仅在全量目录里特征词擦边命中，如说"电机"匹配到"L298N 电机驱动模块"）——候选人选首位标注"猜"
   - **现象模糊**（只有"坏了/不行了/有问题"这类词，没有"完全不转/读数为 0/发烫"这类具体现象）——即使物料已定位也要问现象
   - 澄清内容按需组合：缺物料问物料（候选项 chips），缺现象问现象（常见现象 chips），都缺一起问
   - 澄清只允许一轮：用户补充后仍不足 → 按最可能理解回答，并在开头明示假设
3. 定位到（或用户补充后）→ **本地检索**该物料知识卡片/社区经验 → 有命中 → LLM 综合生成（provenance=local_kb，带卡片引用）
4. 本地未命中 → **联网检索**（物料名+问题）→ 有结果 → LLM 按检索摘要生成（provenance=web，附来源链接）
5. 联网也失败 → LLM 通用知识回答（provenance=model，提示"本地未收录，以下为通用经验"）；LLM 整体不可用 → 预置兜底（provenance=offline）

### recommend（愿望到方案）

现有五步管线不变（意图理解 → 物料目录限定选择 → 库存校验 → 技能路径 → 一键预约），
结果在对话中以 BOM 卡片内联展示。项目描述过于模糊（少于 5 个字且无名词）时可反问一句想要什么功能。

### inventory（查库存）

现有流程不变（名称/型号/分类匹配物料 → 报库存位置）。

### chitchat（开放式问答）

无槽位检查，直接走"本地检索 → 联网检索 → 通用经验"阶梯（同 troubleshoot 的 3-5 步）。

## 澄清规则（细节）

- 一次只问最关键的**一个**问题；候选项做成可点击选项，降低输入成本
- 待澄清状态存 `pending`：原始问题 + 已识别槽位；用户下一条消息视为补充信息，与原始问题合并后重走流程
- **"都不是，是我自己的物料"不等于信息已知**——它只是排除了系统内物料，必须再追问一句"它叫什么、什么型号"，拿到名称后按外部物料处理（禁止再拿目录里的物料硬套），回答走"本地→联网"阶梯（本地大概率无收录，即联网检索该型号）
- 澄清最多两轮（第一轮槽位、第二轮仅当"自带物料"追问了名称）；两轮后信息仍不足 → 按最可能理解回答，并在开头明示假设
- 澄清状态存在后端内存（按 conv_id），服务重启即失效——前端表现为"再问一次就好"，可接受

## 对话状态约定

- 前端进入对话页时生成 `conv_id`（页面生命周期内不变，刷新页面重新生成）
- 后端按 `conv_id` 保存 pending 状态（内存字典，演示规模无需落库）

## 回答展示约定（前端）

- provenance 徽标：local_kb=绿色"本地知识库"、web=蓝色"网络检索"、model=灰色"通用经验"、offline=黄色"离线兜底"
- 澄清消息：气泡 + 候选项 chips（点击即发送）
- 排障回答：保留"多智能体协作过程"steps 展示（澄清也记入 steps）
